## 0. 开工要求：先看实际画面，再修改

检查最新工作区和相关源码，保留用户已有修改。只读需要的文件，先看 `AGENTS.md`、`package.json`、当前场景入口、样式、资产与内容配置。旧 README 和 `public/ART_DIRECTION.md` 是历史资料，不是本版架构或风格的上限。

启动当前版本，至少观察：第一屏、相册、钢琴 / 舞蹈、狮子章节、蛋糕、每一次连接；能运行则录制一段实际操作，标注问题发生的画面和时间。不能运行时说清原因，先完成不依赖该环境的设计与代码，不假装已经看过真机效果。

**后续执行方式：** 分阶段交付可运行结果，每批包含具体画面与交互证据。先定方向、做代表性样章，再扩展四章；不要一次堆完所有功能才问“美不美”。

本轮修改范围内允许更换旧模型、组件结构、场景组织和制作工具；不必保守沿用旧影片方案。软件和必需素材以免费、可合法取得为原则；不得私自购买插件、订阅、云渲染或模型包。已允许使用本地软件，但“有安装授权”不等于你已经有能力远程操作用户电脑，按实际工具能力执行并说明。

### 1.2 明确废止的旧假设

**不再要求所有内容是三维，不再要求所有章节共用一个 Three.js 场景对象，不再把 GitHub Pages 的资源体积当制作边界，也不把 WebGPU 当作画质保证。**

旧 V2 中“狮子也转精细 3D”的建议已被用户后续的 2D 方向覆盖；旧“影片播放驱动角色”的实现不作为正常交互方案。全片统一的是导演、美术和体验，不是文件格式。

非互动的极短环境插镜，可以在确有必要且用户体验通过时采用离线影像，但必须标为辅助表现，有静态退路、不等待播放器、不承担核心输入反馈。默认先不用它，不能借这个例外把钢琴、双人舞、摸狗和狮子互动重新换回 MP4。

### 1.3 可由你直接决定，不必重复提问

具体布局、免费工具、渲染器评估、绘景层数、非关键服装细节、镜头曲线、UI 尺寸、动画实现、资源优化和合理架构重构，由你给出最优方案并以样章验证。

最终域名、云端账户、付费行为、私人内容是否公开、具体收礼日期不擅自决定。未知机型和电脑配置在首次真机 / 本地重型制作前补充，不阻塞先做前端和视觉样章。

## 2. 产品定位：会活过来的电影绘本

观看者不是在浏览一个展示作品集，也不是在玩计分游戏。她像被邀请进入一本专门为自己准备的故事书：纸张、光、回忆和角色逐渐活过来，最后回到生日桌面。

**主要体验是观看、触碰与停留，界面不抢戏。** 每章保留一个清楚的主视觉和一个当下最重要的动作；其他控件低调但可发现。自然语言提示解释“点哪里会发生什么”，不解释技术。

### 2.1 四章的媒介配置

| 段落 | 主媒介 | 精力应放在哪里 | 不要做什么 |
| --- | --- | --- | --- |
| 魔法邀请 | 精绘背景的 2.5D 层景 + 局部实体卡片 / 魔杖 | 第一眼、纸与蜡、烛光、真实跟手、宠物登场 | 为远景建整座城堡；长时间飞越；背景图上堆大按钮。 |
| 回忆相册 | 精致 HTML/CSS 排版 + 纸面变换，必要时局部网格翻页 | 字体、留白、照片、页边、触摸与阅读 | 所有正文烘焙成糊贴图；各种风格卡片混排；滚动劫持。 |
| 钢琴 / 双人舞 | 两位角色、钢琴、路灯和地面精细 3D；远景分层绘景 | 脸、眼、手、黄裙、落脚、相互回应、连续机位 | 低精人物塞入小窗口；独立播放影片；复制一对舞者。 |
| 书信 | 稳定的纸面阅读 + 少量环境变化 | 真实文字、阅读空间、声音退让 | 长篇强制打字机、自动跳走、上方角色持续抢戏。 |
| 狮子章节 | 精绘 2D 角色动作 + 2.5D 多层草原 | 1994 气质、轮廓、表情、动作状态、前后景纵深 | 电影整片切段、扁平贴纸、几何狮子或写实皮毛。 |
| 蛋糕 / 结尾 | 精细局部 3D 或经批准的等效 2.5D + 实时烛火 / 烟花 | 奶油、光、许愿因果、最后一屏的完成感 | 塑料圆柱、全屏礼花遮字、完成后只剩两个按钮。 |

局部替代技术只要不破坏已确认交互、画质和连续性，可以采用。人物手部与双人接触是需要可信空间关系的重点，不应优先用平面序列敷衍。

### 3.1 参考研究必须产生的交付物

为本项目制作一张方向板和一张反例板，覆盖四章、人物、小狗、狮子和蛋糕。每张参考写出具体借鉴点，如“人物占画幅”“纸张层级”“蓝金关系”“牵手转场”，不只写“高级”。

同时做 4 张同尺寸竖屏关键帧，分别代表四章。把它们并排看：字体、按钮、光色、主体尺度、材质观感必须像一个作品。**四张静帧就不统一时，不进入大量动效制作。**

商业参考用于审美研究，不当可下载素材库。不要运行抓站脚本把它们的角色与贴图装进项目。公开源码按对应许可证使用并记录，不假定源码许可覆盖所有美术素材。

## 4. 全片美术规范

### 4.1 色彩脚本

以下是设计起点，可以在统一方向板审稿后微调，不是每章独立选色。

| 共享角色 | 起始色值 | 用法 |
| --- | --- | --- |
| 午夜蓝 | `#141B2F` | 夜景母色、阅读外环境与深色界面。 |
| 象牙纸白 | `#F4EBDD` | 卡片、相册、书信共同纸色；照片不强制染色。 |
| 烛光金 | `#D8B56D` | 主视觉引导、烫金、暖边缘光，克制使用。 |
| 暮色紫 | `#67618A` | 第三章环境，不把皮肤和白衬衫整体染紫。 |
| 草原赭金 | `#BE864E` | 第四章土色与晨光，与全片烛金相接。 |
| 封蜡深红 | `#793D42` | 第一章与书信呼应，不新增大面积跳色。 |

2D 绘景与 3D 灯光对照同一套色板。3D 的色彩空间 / 色调映射明确一次处理，2D 与照片按正确图像色彩解释显示，不给 DOM 再套一层重复 tone mapping。用相同输出条件的屏幕截图校准，而非要求不同引擎使用相同数值就认为一致。

### 4.2 主体、光与质感

每屏只保留一个明确的主要注意点。景深和暗部是服务构图，不是隐藏粗模。角色脸、手、眼与脚的审稿版本必须有无景深 / 无强泛光的画面。

暖光与冷影贯穿全片，接地阴影合理；人物和狗不能像无影贴纸浮在背景上。2D 角色也有画进动作中的接地影或独立影层，方向与背景一致。

纸张、皮肤、衬衫、黄裙、卷毛、奶油、蜡和金属有不同触感。避免所有物体同样光滑。胶片颗粒只作极轻的可选视觉统一，不施加到正文和照片大图上，不使用大面积昂贵 CSS filter 来模拟整套电影后期。

### 4.3 字体、排版和 UI

优先一套清晰中文正文字体 + 一套有书卷气的标题字体，许可核验后本地分发所需网页字体。正文可用 iPhone 合适的系统中文字体回退，不能等待大字体文件后才出现文字。

建议设计 token：

```css
:root {
  --ink: #141b2f;
  --paper: #f4ebdd;
  --accent: #d8b56d;
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;
  --space-8: 2rem;
  --body-size: 1.0625rem;
  --body-leading: 1.8;
  --motion-feedback: 120ms;
  --motion-panel: 280ms;
  --motion-page: 620ms;
}
```

这些是起始值，不是把所有动画一律设成相同时间。交互反馈要即时，视觉收尾可更慢；不能用 `120ms` 的防抖延迟琴键发声。

正文默认约 17–18 CSS px，标题按屏幕自适应，避免大标题挤掉人物。正文纸面宽度有限，长文不铺满桌面整个屏宽。尊重文字放大，重点按钮命中区域尽量达到约 44×44 CSS px；琴键可通过有限音域和合理布局做到手指可操作，而不是塞满 88 键。

常态控件只保留声音、返回 / 章节入口和当前必要操作，样式统一。不要做后台式导航栏、技术徽章、帧率面板、播放时长卡片或一排“体验升级”宣传标签。调试信息仅开发模式可见。

### 4.4 明确排除的视觉形式

不做通用 SaaS 落地页，不做多列玻璃卡片，不做霓虹描边按钮，不做每段一个圆角“模型展柜”，不做满屏爱心和光点，不用浏览器默认播放器覆盖画面，不靠黑边假装宽银幕，不让文字不断飞入飞出。

桌面可以有更宽构图，手机绝不只是把桌面页面缩小。禁止桌面自定义鼠标光标方案成为手机交互的前提。

## 5. 前端流畅度必须先落在交互架构里

### 5.1 舞台是持久的，渲染器不是无边界常驻

建议使用持久 `ExperienceShell` 承载当前场景和阅读界面，由一个 `ExperienceDirector` 管理章节、镜头、加载、音频和输入交接。

```text
ExperienceShell
 ├─ StoryState：章节 / 相册页 / 信件 / 许愿 / 重播
 ├─ Director：唯一叙事调度与镜头所有权
 ├─ StageHost
 │   ├─ 当前 2D / 2.5D / 3D 场景适配器
 │   └─ 有预算上限的下一场准备或交接快照
 ├─ ReadingLayer：相册 / 书信 / 图片放大 / 辅助内容
 ├─ InputRouter：pointer 所有权与输入取消
 ├─ AudioBus：琴音 / 配乐 / 环境 / 拟音 / 录音
 └─ AssetCatalog + ResourceScheduler：使用 Codex 的 manifest
```

“统一舞台”不等于强迫 Pixi 与 Three 共用一个 canvas / GPU context。默认不要做复杂跨引擎共享纹理。每种渲染器最多一个受管理实例，平时只有当前需要的渲染循环运行；退场后暂停并释放不再需要的 GPU 资源。

跨媒介转场优先用构图匹配与短暂的预备图 / 静帧接管，而不是让两套大场景永久双倍渲染。确有必要短时共存时，必须计入内存和帧时间预算。不要每翻相册一页就销毁重建整个 GPU 上下文。

### 5.2 技术栈决策

| 技术 | 默认态度 | 引入条件 |
| --- | --- | --- |
| React + TypeScript + Vite | 保留成熟的内容 / 界面能力 | 可以重构组件，不因换技术名而重写全部阅读功能。 |
| Three.js | 用于人物、琴、狗、蛋糕等关键空间关系 | 默认兼容路径先可用；运行样章决定渲染策略。 |
| PixiJS | 2D 狮子章节的优先候选，动态加载 | 如轻量现有 2D 层已经满足需求，可不增加依赖；复杂 atlas / 层景才引入。 |
| GSAP | 复用现有动画能力 | 负责明确的 UI / director tracks，不能与另一套系统抢同一变换。 |
| Theatre.js | 可选制作工具，不是强制线上依赖 | 浏览器调镜确实提高效率时再评估；编辑器与运行许可分别核验，生产不带编辑 UI。 |
| MediaPipe | 保留可选手势 | 用户主动启用才加载 / 推理，离开相关场景停止。 |
| 物理、复杂状态库、平滑滚动框架 | 默认不新增 | 必须用具体收益证明，不为一个生日网站堆整套游戏引擎。 |

不要仅因为新 iPhone 可能支持 WebGPU 就默认其更快、所有材质兼容。Three 官方明确区分 WebGPU 与旧自定义着色器 / 后期的迁移，Pixi 官方也区分不同 renderer 的成熟度。[S06–S07]

**决策规则：** 同一人物 / 灯光 / 后期样章，比较实际画面、冷启动、交互帧时间和兼容性；选一种主生产方案，保留明确的兼容退路。不维护两套审美不同的整片版本。

### 5.3 更新循环与所有权

每帧顺序固定：处理输入快照 → 更新故事 / 动作状态 → 求角色姿态 / 视线 / 接触 → 更新导演镜头与灯光 → 提交渲染。声音触发走独立、低延迟的音频入口，不等待画面每一步结束。

一个相机或骨骼的最终变换只能有一个写入者；其他轨道输出目标和权重，不互相覆盖。React 不每帧 `setState` 记录所有骨骼与粒子。DOM 高频位移采用可控 ref / 动画驱动，状态只在语义变化时提交。

相册阅读静止时暂停无关大范围动画；屏幕外、后台和锁屏状态暂停昂贵工作。切回时按当前状态恢复，不补播离开期间的全部动作与音符。

### 5.4 触摸优先级

```text
照片放大 / 正文滚动
   > 当前对象的拖动 / 琴键 / 摸狗
   > 场景空白区域的轻互动
   > 章节导航手势
```

pointerdown 确定所有权，pointerup / pointercancel / lostpointercapture / 失焦 / 换章必须释放。琴键滑奏使用坐标命中，不依赖 pointer capture 后不会按预期触发的跨元素 enter 事件。多指逐一跟踪。

`touch-action: none` 仅用于真正需要接管的魔杖、琴键或局部拖动区域；不整站禁用滚动和缩放。相册横向翻页不抢纵向读文，轻微手抖不触发全局换章；边缘系统返回手势保留空间。

不默认安装全局平滑滚动库，不用滚轮 / 触摸位移强制把用户吸附到下一章。这里的“流畅”首先是操作可预期，而不是所有东西一直运动。

## 7. 第一章：月光下的生日邀请

### 7.1 第一屏的目标画面

手机竖屏首先看到一张经过美术设计的完整画面：暖色书桌、邀请卡与封蜡为前景；中景是烛台、旧书与拱窗；远景是夜色城堡的轮廓。主光落在邀请上，文字可读，暗部有层次，不是一张过暗壁纸。

画面文案先用：“师宝宝，一份只属于你的生日邀请。”只出现一次必要提示。声音按钮可见但不抢中心；不展示模型加载数量、技术介绍或单独的视频开始键。

### 7.2 分镜与实际交互

| 镜头 | 画面与空间 | 用户操作 | 反馈与结束条件 |
| --- | --- | --- | --- |
| INV-01 | 图书馆桌面，克制慢推；邀请占主要注意点 | 点卡片或封蜡 | 即时细小回应并尝试开启音频；声音被限制时仍能进入。 |
| INV-02 | 镜头稳定，卡片可见厚度与铰接 | 轻点打开，或拖动开合 | 拖多少转多少；松手自然吸附到开 / 合状态，不跳回首帧。 |
| INV-03 | 魔杖与少量光轨 | 按住拖动 / 轻点 | 杖尖跟手，灯与金字因施法而变化；不是每点都播同一整段。 |
| INV-04 | 杏色犬探头、奶油色犬走近 | 摸狗或继续 | 两只独立反应；不堵名字、封蜡和翻页位置。 |
| INV-05 | 相册成为当前主视觉 | 点相册 / 向页边拖动 | 进入相册机位，纸声连续，不黑屏切另一张网页。 |

背景以精绘分层为主，前后景视差很轻。不要让手机陀螺仪成为必需，也不要让整屏跟着手指大幅漂移。局部卡片可用 Three 或网格形变，最终要求是手感和质感，不限制一种技术。

### 7.3 验收

首次打开静音可完成；拒绝相机可完成；卡片拖一半取消无错态；魔杖快速划动不积压粒子；两只狗命中范围独立；首屏无默认字体突跳、布局重排和空白模型。

## 8. 双泰迪：不是网页挂件

### 8.1 造型与定妆

做玩具贵宾犬：合适的短口鼻、垂耳、圆润修剪、脚掌、胸腹与卷毛轮廓。杏色 / 奶油色不仅颜色不同，眉眼、耳姿、头部比例和反应节奏也略有区别。

不追求真实犬类牙齿的近景展示，不做过大的玻璃眼、僵硬咧嘴和不自然的人类表情。眼睛被眼睑包裹，高光有方向；头动时视线不是无目标乱转。

### 8.2 毛发与运行方式

优先“大形卷毛 → 中尺度卷毛簇 / 合理几何 → 法线与粗糙度 → 少量轮廓毛卡”，在目标手机上检查逆光、透明排序与远近闪烁。不是把每根离线毛发都原样导出。

小狗是重点互动角色，默认精细 3D。若提出 2.5D 替代，必须先证明能完成持续触摸、视线追随、转头和独立空间回应，且视觉不退化；不可用几个透明短视频直接代替。

### 8.3 状态与性格

```text
idle / look / approach / sit / pet / celebrate / rest
```

杏色主动先回应，奶油色稍慢而温柔。延迟是性格演出，不延迟触摸即时反馈。摸头优先于自主动作，重复输入延续或调整当前反应，不排长动作队列。

触摸结束后头颈、身体、耳朵和尾巴依次自然收回。脚有落点与阴影，转身不滑。阅读时安静趴下或退场；舞蹈时不固定贴在画面角落抢戏。

**样章必须同时有：** 中性光近景、目标场景光、正侧面、走两步 / 转头、分别摸两只狗的实时录屏。静态好看与被摸时不变形都要通过。

## 9. 第二章：精致相册，而不是图片轮播插件

### 9.1 内容与占位策略

顺序保留“初见 → 精选时间线 → 照片 → 小事”的结构，但没有真实资料时不生成虚构初见和纪念日。当前主线用 3–5 张许可清楚的示意网图展示版式；日期和关系字段为空的单元隐藏。

默认网图可选林间光、山景、湖面、城市暮色、花或生活静物，形成清楚的远近节奏。不要拿陌生人的情侣照当作用户合照。图片来源与许可记录在 `docs/ASSET_SOURCES.md`，下载后走本项目资产链，不依赖随机图 API 或长期热链。[S12–S13]

`demo` 模式有一处克制但明确的“示意内容，待替换”提示。终版 personal 模式必须通过内容检查，不能把占位句子当作用户真实经历。

### 9.2 版式

手机一页一个阅读单元：图片、一个短标题和 1–3 句说明。保持固定纸张语言和适当留白，人物照片后续替换时优先保完整人脸和手，不自动强裁。

相册封面、书页、信纸共享纸色与细纹，不为每页发明新卡片样式。页码小而清楚，例如 `2 / 5`。已删除趣梗，宠物只在封面或某一照片页短暂探头。

### 9.3 手感

跟手翻页，拖动速度与距离决定翻过或回弹；低幅手抖不翻页。正文纵向操作、图片大图缩放和横向翻页分开处理。

点图进入同构图的放大层，进入与退出的主图锚点一致。支持缩放、拖动和清楚的关闭入口；退出回原页和原滚动位置。关闭动画不能把照片先缩成一个点再突然消失。

页面稳定后文字立即可读，不强制逐字播放；动画只用于纸面、标题或段落的轻进入。不是整章滚动始终推动摄影机，让人无法安静看图。

### 9.4 末页进入暮色

末页舞台邀请图是一个特殊资产，必须从下一场的批准机位输出，或以一致机位绘制。它不是随机网图，不会被“替换用户照片”流程替换。

路灯、地平线、钢琴和人物位置对齐。照片放大进入屏幕时，先让光或发丝出现细动，再进入真实空间。见第 15 节 TRANS-02。

## 10. 第三章前半：真的在弹琴

### 10.1 空间与人物

蓝紫暮色、山顶平台、远处城市灯海、一盏路灯，男角色坐在钢琴前，女角色在侧面倾听。人物、琴、琴凳、地面和路灯处于同一空间，远景可用精细分层绘景。

人物是略偏写实结构的动画电影角色，不是扫描真人脸，也不是大头玩偶。白衬衫有衣领、肩线、袖口与褶皱，黄裙有布料厚薄、重量和转身延迟；肤色、衣料和轮廓在小屏仍分得清。

既有基底只是候选。脸、手、肩颈或变形不过关就替换相应部分，不因为能导出 GLB 就保留。需查看中性光与目标光下的正面、侧面、微笑、转头、坐姿、手部，不能只提交远景。

### 10.2 手机键盘与音域

先采用一只手能可信覆盖的有限音域，例如 D4–A4（5 个白键、3 个黑键）作为工程默认，实际构图与姿态库验证后可调整。用户没有要求钢琴教学级完整 88 键，不应因此扩大到难以保证指法的范围。

键盘位于安全区上方，尺寸方便 2–3 指；黑键必须可命中、可发声。三维琴键与屏幕按键对应，不允许下方按钮动而场景琴键不动。

### 10.3 输入生命周期

| 输入 | 声音 | 可见琴键 | 角色 |
| --- | --- | --- | --- |
| pointerdown | 立即触发正确音高 | 对应键下压 | 对应手指与手腕进入当前可行姿态。 |
| hold | 合理延音，不每帧重新发声 | 保持下压 | 保持接触并允许轻微身体律动。 |
| pointerup / cancel | 自然衰减 | 独立回弹 | 指尖回到等待 / 下一目标。 |
| 同指滑过键 | 释放旧键、触发新键 | 按轨迹改变 | 手腕与指尖连续调整。 |
| 多指 | 2–3 音独立处理 | 每键独立状态 | 当前音符集合合成为一只手的可行姿态。 |
| 离章 / 失焦 / 后台 | 清空 held notes，防黏音 | 全部合理释放 | 进入明确稳定姿态。 |

同键多指需持有计数或同等正确模型，一指松开不截断另一指；重复击同一键应能产生新攻击，不让一个旧 voice 永久占住按键。限制最大复音与 voice 生命周期，防止长时间演奏积累节点。

### 10.4 动作实现

使用制作端的姿态库 / 命名动作作为基础，加运行时指尖目标与手腕调整。主身体动作、手指、视线、脸和衣物二级动态分层。每次按键不是触发一段完整摆臂动画。

音符先响应，不为了等待手从远处移动而延迟声音；因此演奏手平时停在合理待命范围，有限音域的最远跳键也需要设计过渡。任意三音不自然时修姿态或音域，不用手指穿键掩饰。

女角色对乐句和持续演奏作反应，不每个音都疯狂点头。表情先于大动作，眼神在琴键、对方和舞台空间中有目标。

### 10.5 零输入与乱按

没有输入时不假装用户仍在演奏。角色呼吸与等待，背景轻声留白。乱按时声音跟随实际输入，身体从当前姿态连续合成，不排 20 个过时动作。

可选引导一句旋律，不能要求弹对才允许继续。用户弹出的音高不被偷偷纠正成预录曲。背景配器避让琴声，让“正在操作”听得出来。

### 10.6 验收

任意 3 音 → 停 → 双指 → 单指松开 → 快滑 → 三指和弦 → 失焦再回来。检查声、键、指尖、表情和无黏音。必须同时交付可操作网页与真实输入录屏，不以 Blender 影片代替。

## 11. 第三章中段：触摸伴奏驱动的双人舞

### 11.1 明确采用用户的①选择

弹琴阶段驱动坐着的琴师；牵手进入舞蹈后，两人离开钢琴，屏幕键盘代表观看者的触摸伴奏，继续驱动舞步。不要出现同一个男角色一边坐着弹琴、一边又在远处跳舞。

舞蹈阶段的界面可以把较实体的键盘轻量化为同一套精致伴奏键，但保留实际可弹音高与触摸反馈。不要新增“播放舞蹈”的按钮替代输入控制。

### 11.2 编舞与镜头

| 段落 | 动作 | 摄影 |
| --- | --- | --- |
| 起身与邀请 | 从琴凳起身、走近、伸手；女角色先看手再看他 | 从琴侧平移到双人空间，人物不瞬移。 |
| 并肩侧步 | 轻快侧步与小踢腿，彼此试探、呼应 | 全身中景，看清鞋底与姿态，城市不抢人。 |
| 转向与牵手 | 转向对方、握手、引导转身 | 短暂看手部，再回全身；不把关键舞步裁掉。 |
| 黄裙旋转 | 裙摆与头发有延迟，身体重心稳定 | 轻微顺着动作移动，不持续绕圈。 |
| 相视收势 | 自然落脚、呼吸和目光停留 | 慢慢稳定下来，准备把注意力移向信。 |

单轮编舞约 20–35 秒的实际动作时长，用户停顿不算。可以继续玩，不能无限自动循环同一段。

### 11.3 节奏映射

输入密度、最近间隔和最近输入时刻用于控制**统一动作相位**。初始节奏速度范围可试 0.85–1.15 倍，再按画面调整；不要用户一顿乱按就变成鬼畜倍速。

停手后在下一个短而稳定的落脚 / 接触节点进入收势或等待。重新弹奏从可连接姿态起舞，不能退回第一帧。动作安全收尾通常应在约 0.3–0.8 秒内有清楚回应，精确值依编舞；不能用户已停几秒人物还在追播。

### 11.4 双人接触

两位演员共用舞蹈相位、地面与接触锚点。不能分别随机选择两个“dance” clip 后希望手刚好握住。脚底锁定、骨盆重心、手掌方向和牵手约束必须一起考虑。

在 Blender / 制作端先把双人动作排准确，运行时只做受限速度、衔接和少量修正。IK 不是所有编舞质量的自动保证。裙摆可以用辅助骨 / 形变 / 已验证的二级动态，不强制手机实时布料模拟。[S08]

### 11.5 到书信的情绪落点

收势后先对视，音乐在乐句处退下，目光转向钢琴旁的信封，镜头再跟过去。信在刚才建立的空间里，而不是页面底部突然新增一块内容。允许跳过舞蹈直接读信，并使用较短但有意义的衔接。

## 12. 第三章后半：让书信安静下来

暖白纸、深红封蜡、“师宝宝亲启”。点封蜡即可拆开，拖动只是可选辅助。信纸展开后全文可读，阅读区域稳定，正常纵向滚动。

标题 / 落款可少量手写感，正文使用清楚的中文字体。不要把阅读文字做成低分辨率贴图，不用长篇打字机动画，不让背景镜头持续移动。

配乐明显降低，留少量纸声或环境。录音文件存在时显示“听听这封信”的主动入口，可暂停 / 重听；没有录音不展示假按钮，不采用陌生合成声音冒充用户。全局静音控制它，离章停止。

保留称呼、段落、结尾、落款和可选录音的独立配置，当前填示意祝福并标注。不得自动添加求婚、纪念日或未提供的承诺。

正文后出现“最后，一起许个愿”；回看保持合理阅读位置，不自动计时跳章。此处的美感来自停得住、看得清、声音退得下去，不再加更多效果。

## 13. 第四章：1994 气质的互动 2D 狮子章节

### 13.1 方向固定为 2D / 2.5D

手绘角色、清楚线条与色块、暖色草原、紫蓝远山、眉眼与口鼻表演、分层摄影。必须显现 1994 动画版的情绪和角色气质，不用写实狮子加滤镜代替。

这里“2D”不是降低标准。轮廓不抖、角色不变脸、各动作体积一致、表情有戏、动作有预备与收势，才比粗糙三维更好。

原作角色与电影截图 / 原片 / 原声的文件权利分别核验。重新绘制、AI 生成或个人送礼用途不自动解决角色与素材权利问题；公开发布版本需要明确素材来源和使用依据，不提取影视整帧直接当动画图集，也不从商业站点盗取素材。

### 13.2 本地制作方式

优先用 Krita / OpenToonz 做角色稿、关键帧、补间、清线与上色；需要三维空间辅助机位时可用 Blender Grease Pencil。工具按实际工序选，不要求全装。OpenToonz 官方提供可免费使用的开源二维动画制作路线。[S09]

角色动作可采用精绘帧动画与局部变形结合：关键表情 / 转头 / 吼叫用绘制帧，轻微呼吸 / 尾部 / 背景草动可用受限变形。不得用一张图反复拉伸模拟所有复杂动作。

### 13.3 场景层级

```text
远层：天空渐变 / 星空 / 太阳与云
中远层：山脉 / 草原大形 / 河流
中层：树 / 岩石 / 主要地面
角色层：父狮 / 幼狮 / 成年主角 + 接地影
近层：少量草 / 树枝 / 遮挡物
前端层：一句祝福 / 必要交互提示
```

分层视差由统一导演控制；摄影机推近时景物具有合理相对速度，不把每层都随手指同幅度漂移。角色根据站位缩放、遮挡和脚底高度融入地面，不悬浮在中央。

### 13.4 三段叙事与动作状态

| 段落 | 画面 | 输入与状态 | 不能接受 |
| --- | --- | --- | --- |
| 父子清晨 | 暖晨光、岩台，父狮稳重、幼狮灵动 | 点幼狮：转头 → 靠近 → 停住；父狮有目光回应。点晨光：共同看向远处。 | 点一下开始整段不可控影片；父子互不理睬。 |
| 星空记忆 | 从岩台仰看夜空，父亲的象征光影克制出现 | 点亮几颗星即可产生回应，无密码和失败惩罚；相机与音乐安静过渡。 | 死亡 / 战斗再现；把父亲意象强套成用户私人经历。 |
| 成年归来 | 成年主角走向岩台，轮廓与幼体有继承关系 | 按住前行、松开停步；点目标也可到达。点角色：吸气 → 抬头 → 吼叫 → 恢复。 | 幼狮现场拉伸放大；吼声与嘴不同步；松手仍走很久。 |

建议动作状态：`idle`、`look`、`turn`、`walk-start`、`walk-loop`、`walk-stop`、`approach`、`nuzzle`、`roar-anticipation`、`roar`、`roar-recover`。只做必要且好看的动作，不扩成冒险游戏。

状态切换由输入和合法连接点决定。帧序列本身可以预制，但转向、位置、停止、触发和叙事选择必须是真的交互。这与切换 MP4 片段不是同一种方案。

### 13.5 时间设计：动画感与前端流畅分开

角色可按 12 或 24 张绘制帧每秒的风格设计曝光节奏，镜头、位置插值、触摸提示和视差仍由稳定的显示更新驱动。不是直接把整个网页降到 12 fps，也不是随机跳帧。

动作中刻意的持帧和前端卡顿要区分：帧切换均匀、位置连续、输入立即反馈。跑步的脚与地面位移按接触标记匹配，不能在低帧角色下用匀速滑动替代步态。

### 13.6 Atlas 与内存

按动作段 / 角色拆分图集，常规从 2048 边长起步，确有需要再试 4096 并测设备。使用固定 pivot、trim metadata、边缘扩展与足够 padding，避免转头抖动、相邻帧渗色和透明黑边。

图集配置应记录帧名、时长、起点、循环区间、可中断点、脚底锚点和事件标记。生产不加载整部电影的几千帧原图，也不把所有动作全解码常驻。

**下载压缩体积不等于解码内存。** 4096×4096 RGBA8 纹理基础层为 64 MiB，完整 mip 链约为其 4/3；这是尺寸公式估算，不是设备测量。WebP / AVIF 文件小，不代表上传 GPU 后也按文件大小占用。

Pixi 的纹理、缓存与生命周期按锁定版本 API 处理；适时卸载，不在一帧集中销毁全部大图集造成停顿。[S10–S11]

## 14. 第四章结尾：烛火、奶油、远空烟花

### 14.1 从草原回到生日桌面

星光或晨光中的一个亮点逐渐接近烛火的屏幕位置、大小与色温，镜头重新对焦才显露蜡烛和奶油蛋糕。画面回到第一章建立过的桌面 / 窗边，让整片有闭环。

单层奶油蛋糕，颜色以纸白、浅粉 / 杏色为主；裱花有层次、不完全机械规则，水果适量。蜡烛少而精，不公开年龄，不用数字蜡烛猜生日。

### 14.2 许愿状态

```text
lit → extinguishing → celebrating → complete
```

`lit` 安静等待，没有倒计时。用户轻点烛火或明确的等效入口，一次熄灭；连续点击只触发一次状态迁移。

熄烛时火苗收小、细烟上升、光照柔和变化，再进入音乐和庆祝。不要一点击就白闪和全屏彩带。烟花在远空 / 窗外分 2–3 次绽放，约 6–8 秒收束，少量光落到奶油与狗毛，不盖住祝福文字。

两只狗按不同性格回应一次后安静。结尾继续保留蛋糕和环境，不把渲染器清空成一个“完成”面板。文字为“师宝宝，生日快乐”，第二句和落款可替换；按钮为“再走一遍”“重读那封信”，不自动循环。

降低动态效果时保留柔和庆祝光和完整内容，移除密集闪光与大幅运镜。

## 15. 全片转场：逐段制作，不套通用淡出

### 15.1 必做的 7 个连接

| ID | 连接 | 视觉接管设计 | 声音与资源条件 |
| --- | --- | --- | --- |
| TRANS-01 | 邀请 → 相册 | 同一纸张 / 封面成为相册；页边自然掠过，机位接到纸面阅读 | 纸声连续；下一页和字体布局先就绪。 |
| TRANS-02 | 相册 → 暮色舞台 | 同构图照片变成真实场景：地平线 / 路灯 / 人物锚点对齐，再出现纵深 | 短音色先引导；模型、纹理、必要 shader 已预热。 |
| TRANS-03 | 弹琴 → 舞蹈 | 同一人物起身走近、伸手；镜头从琴侧转向全身 | 琴音尾音过渡为伴奏，人物不复制。 |
| TRANS-04 | 舞蹈 → 书信 | 先收势与视线引导，再抵达场景中已有信封；纸面展开后镜头停住 | 在自然乐句退出，读信音量降低。 |
| TRANS-05 | 书信 → 2D 草原 | 信纸末页的草原插画占画面，草和天空逐渐运动，角色进入 | 风声提前很短出现；2D atlas 已准备。 |
| TRANS-06 | 草原 → 烛火 | 星 / 日光与烛火位置、大小、色温匹配，随后揭示蛋糕 | 草原退下，温暖尾音延续，不能突然狮吼接生日曲。 |
| TRANS-07 | 熄烛 → 片尾 | 不换页，烟花、狗与祝福在同一世界里发生 | 音效和生日主题只进入一次。 |

大多数图像连接先按约 0.8–1.6 秒排，起身和牵手按动作所需更长。不要所有转场都固定 600ms。逆向回看可更短，不要求倒放整段身体动作。

### 15.2 每段的正式配置

```ts
interface TransitionShot {
  id: string;
  from: string;
  to: string;
  requiredBundle: string;
  durationHintMs: number;
  anchorNames: string[];
  interruptPolicy: "latest-intent" | "safe-point";
  reducedMotion: "match-cut" | "short-dissolve";
}
```

每段另有实际镜头 / alpha / 光色轨道和声音 cue，不把所有东西塞进这一张接口。屏幕锚点用规范化位置表示，并分别验竖屏、横屏；转场中 resize 应重新求端点或采用稳定退路，不能把旧方向的快照直接拉伸。

### 15.3 生命周期与最新意图

```text
prepare → ready → enter → active → exit → release
```

`ready` 不止 HTTP 下载完成，还包括必要的图片解码、模型解析、图集上传和实际渲染准备。准备失败留在当前可用画面，给“重试 / 继续阅读”，不把用户锁在不透明幕布后。

新导航请求取消旧的异步提交。已经开始的接触动作按安全点收束，普通过场采用最后一次有效意图。旧请求即使稍后返回，也不能把章节切回去。旧背景音不继续残留。

支持减少动态效果时仍触发同样的语义完成事件，不能因跳过动画导致信永远打不开或许愿状态不完成。

### 15.4 2D / 3D 接管技术

优先在制作端导出下一镜头的匹配图，或在运行时少量生成受控快照。不是每帧 `readPixels()` 或把整个画布转图片。快照是转场桥接，不是核心表演替代。

若运行时捕获受限，使用已发布且与相机配置同版本的图片。让绘景、机位和对应 asset release 一起更新，不能只换模型后继续使用旧照片桥接。

2D 与 3D 的曝光、颜色、缩放和 alpha 边缘单独检查。匹配点不应该突然出现双影、角色尺寸跳变或浓淡不一的紫色滤镜。

## 16. 音乐与声音：同一部作品的听觉

建立一个主题动机，四章改变配器，不是四首互不相关的背景歌。魔法用轻钟 / 柔和弦乐；相册稀疏钢琴；舞台轻爵士律动；草原温暖和声 / 风声；结尾自然落到生日主题。

建立一个总音量和五类总线：`piano`、`music`、`ambience`、`foley`、`voice`。犬叫、狮吼、烟花也服从总静音。界面中的静音状态与实际声音一致。

首次触摸在用户操作上下文里创建 / 恢复音频；后续如果系统挂起，轻提示恢复但不阻塞主线。不能承诺浏览器首次加载就自动有声。[S14]

琴声优先，背景降低并避让音域；弹奏声音不排在动画之后。朗读时进一步压低配乐。长配乐和旁白按媒体播放策略节制解码，低延迟琴音才使用必要的预解码短采样，避免所有分轨一次解码进内存。

事件音效有因果：开卡、纸、键、脚步、封蜡、火焰。不要每个 UI 点击都响“叮”。禁止跨章叠两首主旋律、重复重播叠加音轨和后台回来追播。

音源采用许可明确或原创内容。用户未来录音保留原件，本地轻量降噪和音量整理，不擅自深度变声。没有录音就隐藏入口。

## 17. 手机布局与可访问性

### 17.1 画幅

竖屏优先，横屏另有机位 / 排布，不靠裁切保留头脚。舞蹈全身和牵手范围必须可见，演奏时手和琴键可辨。舞台占据足够视野，不能只剩中间一个小模型窗口。

使用适合移动浏览器的动态视口与 safe-area 处理，避免底部手势条盖住键盘；地址栏展开 / 收起时舞台不反复跳大小。不要因每次 visualViewport 变化重建全场景。

优先稳定机位，不自动检测手指微移就摇晃相机。照片和信件保持正常滚动与字体放大。浏览器返回、关闭大图、返回章节三者有清楚层级。

### 17.2 界面语义

DOM 保留全文与主要操作的可读名称；场景中的“点信封”有等效清楚入口。键盘、静音、返回、重试都可使用辅助技术识别。不要只用颜色表示选中和成功。

尊重 `prefers-reduced-motion`，关闭大幅运镜和频闪，不删除剧情。静音、减少动态效果和没有摄像头都能完成所有四章。

应用内浏览器实际测试；如确实遇到不可支持能力，给简短的“在 Safari 中打开”说明和完整阅读退路，不在尚未失败时一上来强迫跳转。

## 18. 性能与加载预算：先给数字，再用实测修正

下面均为本项目的首轮工程目标，**不是已测成绩，也不是浏览器厂商保证**。实际 iPhone 型号、系统、刷新率、低电量模式和网络需与结果一同记录。

| 指标 | 首轮目标 | 不可混淆的边界 |
| --- | --- | --- |
| 标准画质 | 以 60 fps 体验为目标；固定 60 Hz 观察窗口，rAF 帧间隔 P95 约 ≤22 ms、P99 ≤33.4 ms，避免连续可见卡顿 | rAF 统计是调度指标，不等于精确 GPU 渲染时间。 |
| 重型镜头 | 优化后仍力争维持同一顺畅等级；不足时先降低次要效果 | 稳定 30 fps 可作明确降档，不冒充标准画质达标；不以波动 45 fps 自动视作通过。 |
| 触摸到视觉 | 核心即时反馈 P95 ≤50 ms | 角色自然收势时间与即时反馈延迟不同。 |
| 琴音 | 手机扬声器物理触摸至可闻反馈 P95 ≤100 ms 目标 | 浏览器事件到音频调度并非实际出音；蓝牙耳机独立记录。 |
| 首屏 | 冷缓存、约定 20 Mbps / RTT 80 ms：约 3 秒有效首屏、5 秒核心入口可操作 | 是网络条件下的目标，不承诺所有网络。 |
| 首屏关键传输 | 约 3 MiB 起步，超过约 5 MiB 复核 | 名称和基础内容不得等待整个 3D 包。 |
| 单章新增传输 | 约 8–20 MiB；重点舞台可按证据放宽 | 只在下一必要段落加载，不一次拉完。 |
| 完整主线运行资源 | 约 60–120 MiB 起步，约 150 MiB 复核 | 不等于 R2 总占用，本地高模与历史版本不计入。 |
| 应用 GPU 资源估计 | 常态先按约 150 MiB、交接峰值约 220 MiB 警戒线评估 | 只计应用可估资源，不等于 iOS 系统总内存上限；必须实际测。 |
| 运行稳定性 | 至少连续 10 分钟，包含多次回看 / 重播 / 后台恢复 | 不只测空场景 5 秒平均帧率。 |

预算是用来提早发现问题，不是鼓励无意义的极限压缩。脸、手和主体轮廓优先保质量；首先削减无关远景、过多透明层、实时反射、阴影分辨率和过重后期。

### 18.1 资源调度

```text
应用外壳与首屏
  → 当前场景 critical 资产
  → 当前场景 deferred 资产
  → 下一小段 critical 资产
  → 非必要内容保持未加载
```

下载、解码、转码与 GPU 上传分别排队；初期并发从 2–4 个合理任务起步，根据测量调整。预取不占满网络，也不在琴键操作密集时同时上传几个大纹理。

资产先具备可呈现状态再换场，不用全屏 Loading 百分比掩盖网络组织问题。但超时 / 失败必须诚实显示重试，不让“漂亮等待动画”无限循环。

### 18.2 具体优化优先级

1. 清掉未引用旧影片和重复依赖；首屏不加载手势模型、整套角色和全部音轨。
2. 让模型与纹理有可管理尺寸，采用合适压缩；每种压缩验证实际观感和解码成本。
3. 合理控制 draw call、透明毛卡、全屏遮罩和多层后期；不要只数多边形。
4. 一次语义事件对应一次状态更新；避免 React 每帧重建大树和频繁布局测量。
5. 对频繁粒子 / 临时对象池化，纹理释放分批，重播不持续增加材质和 AudioNode。
6. 阴影与远景能预计算就预计算，动态光只服务当前动作。
7. 画质切换有迟滞与稳定窗口，不每几帧升降 DPR；阅读文字不跟随低分辨率 canvas 变糊。

不把 WebGPU、Cloudflare 或某个框架名字当作性能证据。CDN 改善分发，不改变 iPhone 的 GPU 上限。

| Audacity / LMMS | 录音整理、原创配乐和分轨 | 仅选用可免费取得、许可明确的音源。 |
| glTF Transform / 纹理工具 / 自写打包器 | GLB、纹理、atlas 与 manifest | 复用仓库已有能力，不建十套同功能脚本。 |

工具与资产的许可证分开检查。Blender 的控制器、物理、程序节点等不应被假定会完整进入 glTF；运行动画、形变、灯光 cue 和焦点需要明确导出 / 烘焙 / 重建策略。[S08]

Spine、付费角色平台、商业动作捕捉、收费字体或云渲染不得作为必需依赖。免费软件可减少许可成本，不能代替美术精修。没有能力完成的具体精修应给出源文件、问题位置和所需操作，不用廉价占位冒充终版。

### 19.2 3D 母版到运行资产

```text
方向板 / 定妆
 → 高品质母版
 → 可变形运行网格与 UV
 → 身体 / 表情 / 手指 / 二级动态
 → 角色动作与接触事件
 → 材质烘焙与运行替代
 → GLB + 纹理 + shot / event 配置
 → 浏览器同机位审稿
 → iPhone 实际输入验收
```

制作母版和运行资产分开保存；模型减面、贴图压缩后必须重新看脸、手、衣物和毛发。不要把 Blender Cycles 的截图当成 Web 运行质量已经达标。

### 19.3 2D 母版到运行资产

```text
角色模型表 / 色板 / 表情表
 → 关键帧与动作节奏
 → 必要补间 / 清线 / 上色
 → 分层透明序列
 → trim + 固定 pivot + atlas 分段
 → 动作时长 / 事件 / 接触锚点 JSON
 → 实时状态控制与多层场景合成
 → 手机观察边缘、帧稳定性与输入响应
```

AI 可以协助草图和制作，但未经修正的逐帧生成容易发生外形变化；最终必须检查脸型、鬃毛、体型、线条和光线一致性。不能仅凭“生成了几百帧”视作角色动画完成。

## 20. 与 Codex 共享的资源接口

**本节与部署文档第 5 节共同构成接口；部署文档为 schema 和 URL 规则的权威版本。** 不另造一个 `CDN_URL` / `MEDIA_HOST` 体系。

### 20.1 公开配置

```dotenv
VITE_APP_BASE=/
VITE_ASSET_BASE_URL=
VITE_CONTENT_MODE=demo
```

`VITE_ASSET_BASE_URL` 为空时使用当前应用基址的 `media/`；远程模式由 Codex 注入实际 HTTPS 媒体根。前端不接收 R2 凭证，不关心桶名。

manifest 为当前站点 `asset-manifest.json`，`schemaVersion: 1`，包含 `releaseId`、`contentMode`、`assets` 与 `bundles`。每个 entry 有 `kind`、`variants.standard`、可选 `variants.lite` 和逻辑 ID dependencies；variant 包含 `path / mime / bytes / sha256` 与可选尺寸 / 解码估计。

```ts
// 由 Codex 的资产层提供；调用前完成当前版本 manifest 初始化。
getAssetUrl("duet.female", "standard");
getAssetUrl("pride.cub.atlas", "lite");
getAssetUrl("memory.01", "standard");
```

逻辑 ID 稳定，物理文件可带 release 和内容标识。`path` 是媒体根下的安全相对路径，不允许在数据里塞任意外站 URL。GLB 外挂贴图、atlas 页面和数据 JSON 的依赖也进清单。

### 20.2 bundle 建议

| bundle | critical | deferred |
| --- | --- | --- |
| `invitation` | 入口绘景 / 卡片必要资产 / 交互短音 | 狗的次要动作、环境细节。 |
| `memories` | 封面、当前页和下一页 | 其余照片大图。 |
| `duet` | 男女、琴、基本场景、演奏与邀请动作、琴音采样 | 次要表情、舞段后半的非必需变化。 |
| `letter` | 信封 / 纸面所需资源、文本布局 | 可选录音。 |
| `pride` | 当前 2D 段落及其图集依赖 | 下一段草原 / 星空资源。 |
| `finale` | 蛋糕、烛火、庆祝必要音色 | 远空烟花细节和非关键装饰。 |

这里只决定语义分组，实际 ID 以生产清单为准。不能把一个依赖未齐的角色当作 ready，不能 critical 列一个 atlas JSON 却忘了其图片页。

### 20.3 资产交付包

Claude 输出到明确目录，例如 `.asset-build/runtime/<release-id>/`，附源清单、依赖、实际尺寸、许可条目和视觉审稿状态。由 Codex 工具计算 bytes / hash、上传 R2 并形成不可变 release。

本地预览使用同样结构，先能独立运行一个完整样章。大母版不进 `public/`，不为了预览把私人源图推到公共仓库。不能假设本机目录会自动出现在 GitHub Actions。

一份体验固定 manifest 版本，后台不偷偷切换到新 release。画面快照与 shot 配置若互相依赖，要一起发布。

## 21. 用户以后怎样替换网图和文字

保留 `src/content/story.ts` 的集中配置思路，兼容现有内容类型；新增字段时提供迁移与默认值，不让用户再改十几个组件。

逻辑上的单张照片数据至少包含：

```ts
interface MemoryItem {
  id: string;
  assetId: string;
  title: string;
  caption: string;
  alt: string;
  focalPoint?: { x: number; y: number }; // 0..1，默认保完整构图
  placeholder: boolean;
}
```

可以用适配层保留旧 `image / description` 字段，不强制用户手工迁移所有历史内容。图片文件替换后重新打包 / 发布，而不是覆盖缓存一年不变的旧对象。

必须交付简明的 `docs/CONTENT_EDITING.md`：图片放哪里、哪个配置改什么、怎样更换正文 / 落款 / 录音、怎样隐藏空时间线、怎样从 demo 切到 personal，以及会触发哪些发布步骤。

制作阶段先放网图，不以等待私人资料为由卡住项目。公开个人内容前要确认访问范围；CORS / 隐藏链接 / 前端口令不构成真正隐私保护。预览截图和代码日志也不泄露私人原件。

| ID | 操作 | 通过条件 |
| --- | --- | --- |
| EXP-01 | 只用触摸走全片 | 不开相机、不装 App、不播放主片也能完成。 |
| EXP-02 | 开卡 / 魔杖拖动并取消 | 当前输入即时影响对象，释放后状态正确。 |
| EXP-03 | 琴键单音 / 滑奏 / 2–3 指 | 音高、实体键、指尖对应，无黏音、漏释放或误切章。 |
| EXP-04 | 舞蹈慢弹 / 快弹 / 停 / 再弹 | 舞步受当前伴奏影响，安全收势，不排旧动作，不松手漂脚。 |
| EXP-05 | 2D 幼狮点按 / 成年狮行走中松手 | 状态可解释，动作与位置 / 声音同步，不是播放整片。 |

| EXP-10 | 减少动态效果 | 内容与语义完整，去掉大幅动效后仍可完成。 |

### 23.3 性能与异常

| ID | 检查 | 通过条件 |
| --- | --- | --- |
| PERF-01 | 冷启动与热启动分别记录 | 网络条件、关键传输量、有效首屏与可操作时点明确。 |
| PERF-02 | 最重场景与跨媒介交接 | 记录帧时间分布与卡顿，不只报平均 fps。 |
| PERF-03 | 连续 10 分钟，多次重播 | 无持续增长的贴图 / 音频 / 监听器，无明显热后体验崩坏。 |
| PERF-04 | 拒绝一个资源请求 / 解码失败 | 保持当前可用画面、可重试或明确阅读退路，不显示空模型。 |
| PERF-05 | 降档 | 先降次要效果，文字与关键互动保留；不偷偷改成影片。 |
| PERF-06 | 真实 iPhone | 型号、系统、浏览器与测试方式可追溯；模拟器结果不冒充真机。 |

数字能说明技术质量，不能替代用户审美判断。用户明确指出“不好看”时，应定位并修正造型、构图、材料或动作，而不是用测试通过与他争论。

## 24. 分阶段实施与交付件

### 阶段 A：实际基线与统一设计

观察当前页面，输出少量关键问题；制作四章方向板、共享 token 与 7 个转场的小型分镜。用网图占位补齐前端版式，不等私人资料。

**交付：** 四张同尺寸手机关键帧、反例板、需要替换的旧资产 / 组件清单、可运行的基础布局。先证明画面统一，不先造庞大引擎。

### 阶段 B：有代表性的高质量样章

同时覆盖“最重要的品质”与“混合媒介的接缝”：泰迪近景与触摸；人物单手弹琴 / 起身 / 牵手；相册到暮色转场；2D 幼狮转头与走停；书信到 2D 草原的连接。

可先拆分提交，但必须最终形成一个能连续操作的样章。粗模可以做内部验证，不能把它作为用户应批准的最终画质基线。

**交付：** 可操作预览、资产母版 / 运行包、同镜头截图、真实操作录屏、已有性能数据和未测项。

### 阶段 C：全章节实现

按已通过的统一规范完成第一章、完整相册、第三章演奏 / 舞蹈 / 信、2D 狮子三段、蛋糕与烟花。补齐恢复、重播、返回、失败和减少动态效果。

**交付：** 一条完整 3–4 分钟标准路线，所有真实操作保留；正文和照片替换说明；无旧主片依赖。

### 阶段 D：前端打磨与真机性能

逐段审阅正常速度和慢放录屏，处理瞬移、接地、眨眼、透明边缘、卡顿、层级、字体跳动、音轨连接和安全区。与 Codex 检查远程模式，不能本地好看、线上首屏卡住。

**交付：** VIS / EXP / PERF 结果、具体设备记录、最后的未决问题、可公开资源清单。不能把未做过的真机项目打勾。

### 阶段 E：内容替换与发布交接

当前先用网图完成 demo。用户提供私人素材后按相同接口替换、核对公开范围；Codex 负责资源发布与生产站点。Claude 不临时修改域名、密钥或部署方案。

**交付：** 最终确认截图、对应 asset release、内容配置、读取 / 重播状态检查、可回退版本。

## 25. 不确定问题与失败处理

不再重复 156 个选择题。多数导演和技术细节已授予自由度，先给可观察的结果。只在以下情况集中提问：确实需要付费；真实个人内容的公开范围；收到的两项需求无法同时满足；当前运行环境无法取得关键资产或完成某项操作。

视觉失败按原因处理：

| 症状 | 回到哪里修 |
| --- | --- |
| 恐怖谷 / 表情不适 | 眼睑、眼神、嘴部、脸型、表情曲线与灯光，不是加模糊。 |
| 狗不像泰迪 | 身体 / 口鼻 / 耳朵 / 毛发轮廓，不是换毛色。 |
| 2D 角色像贴纸 | 接地、遮挡、pivot、动作体积和层景，不是多加粒子。 |
| 舞蹈假 / 人物漂 | 编舞、双人相位、脚底和手接触，不是只减速。 |
| 四章割裂 | 共享画幅、纸面、颜色脚本、光与镜头桥接，不是套一个全局滤镜。 |
| 转场卡 | 下载 / 解码 / 上传 / shader 预热与双场景峰值，不是延长黑幕。 |
| 前端“很忙”但不高级 | 减少无动机动效、留白与注意力竞争，让重点更清楚。 |

不得说“安装几个工具就保证达到院线质量”。同样不能因为目标高，就把粗糙结果包装为已经足够。减少次要动作和远景范围，优先保住主体与连续性。

## 26. 最终交付格式

每批结束按以下内容交接，避免冗长重复日志：

```text
本批完成：具体场景 / 操作 / 视觉问题
修改位置：主要文件与资产
查看方法：实际存在的本地入口或预览 URL
画面证据：关键帧 + 实际输入录屏
验证：运行过的检查、设备与结果
尚未通过：具体画面 / 时间 / 原因，不写空泛“继续优化”
交给 Codex：source manifest、运行目录、release 信息与新增依赖
下一批：只写一个明确的阶段目标
```

不要只交代码；不要只交视频；不要只交设计图。完整交付是**可操作网页 + 一致的源资产与配置 + 能核验的画面和测试证据**。
